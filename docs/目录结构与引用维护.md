# 目录结构与引用维护

检查日期：2026-11-24。本文记录当前目录及本轮引用修复；“建议”均为后续方案，尚未实施。

## 当前结构与本轮修复

正式开发在 `apps/api` 与 `apps/web`；`backend` 保留内部 Python Agent；`apps/TeamFlow` 是原项目独立 Go 模块。当前无需引入新的框架、包管理器或工作区配置。

Go 中以下包已迁至 `apps/api/internal/infrastructure`，入口、处理器、服务、仓储、基础设施内部以及现有测试的 import 已同步：

| 旧 import | 当前 import |
| --- | --- |
| `teamflow/internal/config` | `teamflow/internal/infrastructure/config` |
| `teamflow/internal/faults` | `teamflow/internal/infrastructure/faults` |
| `teamflow/internal/httpx` | `teamflow/internal/infrastructure/httpx` |
| `teamflow/internal/platform` | `teamflow/internal/infrastructure/platform` |
| `teamflow/internal/security` | `teamflow/internal/infrastructure/security` |

本轮仅修复 Go 引用及相关说明，保留重构后的布局；不创建旧路径兼容包。公开 API、鉴权规则、数据库结构与数据所有权不变。测试文件仅调整 import。回退本轮修复时应成组恢复引用，并与对应目录版本配套，避免恢复整个工作区而覆盖其他改动；无数据回滚步骤。

前端 TypeScript 检查和生产构建未发现缺失模块，故未做无必要的目录迁移。CI、Release、前后端启动脚本和 Python 语法检查使用的应用目录仍存在。

后续中间件迁移：请求 ID、请求体限制、panic 恢复及认证 HTTP 适配已提取到 `apps/api/internal/infrastructure/middleware`，`platform` 只负责依赖构造与安装。现有测试所需旧入口保留薄转发，测试文件未随此次迁移修改；`httpx` 的既有 Agent 错误依赖留待后续治理。决策与此次验证记录见 [ADR-0005](adr/0005-中间件职责拆分.md)，下文原有检查结果对应此前目录引用修复。

## 改善建议（按优先级）

### 1. 先明确 Go 契约归属，再调整层级

当前 `service` 使用 `handler` 中的 DTO 和接口；聊天服务与通用 `httpx` 又直接引用 `chat/repository` 的 Agent 错误。它们目前可以编译，但业务契约与 HTTP、具体适配器绑定，继续拆包时容易形成循环依赖。

建议将模块公开 DTO、用例接口和可分类错误放在所属业务模块根包；`service`、`handler`、`repository` 各自依赖它。将组装入口保留为单一位置。具体例子是把 Agent 错误归入 `chat`，使 HTTP 错误映射和聊天服务都无需导入具体仓储。

`faults` 当前只含标准库错误值，逻辑上属于共享业务错误而非基础设施能力；可在这一步一并评估其归属，避免仅因目录名改变而把业务层接到数据库或网络实现上。

这属于模块边界调整，实施前需要 ADR，说明兼容迁移和回滚；本轮未实施。

### 2. 区分 Go 启动组装与底层适配器

`infrastructure/platform` 同时组装业务服务、路由和数据库，职责是启动接线。后续可考虑下面的结构，业务模块不必再按全局技术层拆散：

```text
apps/api/
  cmd/api/                       # 进程生命周期
  cmd/worker/                    # 现有占位入口，尚未实现消费能力
  internal/
    bootstrap/                   # 候选：单一依赖组装与路由接线
    auth/                        # 模块公开契约、领域类型和错误
      handler/                   # HTTP 适配
      service/                   # 用例、所需最小端口
      repository/                # 数据访问适配
    chat/ team/ project/ task/    # 同样按业务能力组织
    infrastructure/              # 配置、安全等技术实现
  api/                           # 公开契约
  migrations/                    # 编号 SQL
```

不建议为了统一目录批量迁移；应结合第 1 项的 ADR 分步做，每步验证包图与行为。

### 3. 前端统一公开入口与代码所有者

当前 `app/router.tsx` 仍深层加载 `features/*/routes/*`，而团队、项目、任务通过 `index.ts` 导入。建议统一公开入口并保留路由懒加载；模块内部直接引用本地文件，避免通过自己的 barrel 产生环。

`features/layout` 与 `features/platform/ui/AppLayout` 都承担布局；可按实际用途改为明确的管理布局与协作布局，并由 `app` 组合。无业务偏向的页面容器归 `shared/ui`，避免所有业务模块都依赖含糊的 `platform` feature。

`src/lib/api/{list,chat,admin}.ts`、`src/store/*`、`src/types/*` 仍承载大量业务代码。建议随功能维护逐步移到对应 `features/<业务>/{api,model}`；`shared/api` 只放 HTTP/SSE 协议与错误处理。不要新增另一份服务端状态。

### 4. 明确新旧应用与依赖的边界

`apps/api/go.mod` 与 `apps/TeamFlow/go.mod` 当前都声明 `module teamflow`，各自运行检查可以通过。若未来将它们同时放入 `go.work`，需要先解决同名模块问题；不要直接把旧项目接入正式后端依赖图。

根 npm 包与 Web 包都声明 Motion，当前 UI 从 Web 构建。建议确认根依赖是否有真实调用方，再选择保留独立包或建立 npm workspace；相应同步唯一锁文件策略。`apps/web/work-package-lock.json` 的用途也应明确，避免与实际 `package-lock.json` 混淆。

根 `npm run dev` 使用 `web:dev && go:dev`，前端常驻进程退出前不会启动 Go。当前按 README 分两个终端启动；后续若调整开发入口，应明确两个进程的退出和清理行为。

### 5. 让目录规则和验证一起维护

当前开发指南、历史 ADR 与已删除计划文件之间仍存在旧路径记录。建议历史文档保留背景并注明替代资料，现行入口文档只链接有效文件，避免恢复重复的进度清单。

包迁移应一次更新源码、测试 import、启动/构建脚本及现行文档。现有前端路由测试仍有静态占位页断言，应在单独获得测试逻辑修改授权后与真实登录/协作流程对齐；不应为通过旧断言取消鉴权。
