## 1. Executive Summary（执行摘要）

### 1.1 问题陈述

企业制度、产品说明和运维资料分散在文档中，员工需要反复搜索、阅读和询问同事才能确认答案。直接使用通用大模型又难以保证答案来自企业资料、引用可核查以及访问范围符合员工权限。

上述痛点是现有项目定位对应的需求假设，尚无用户访谈、使用量或节省时间的实测数据。

### 1.2 产品方案与价值

提供一个单企业部署的知识库问答平台：管理员维护成员、授权和文档；员工在被授权的知识库内提问，获得流式答案及可查看的原文片段；维护者通过入库任务、运行记录和聚合统计定位失败。

产品核心价值是把“找到资料—理解内容—核对出处”连接成一个可追溯流程。Agent 的检索、纠错和反思能力服务于答案质量，不以展示复杂内部推理或功能数量作为产品完成标准。

### 1.3 用户与部署边界

- 首版面向一个企业内部的员工与知识管理员；中文界面、中文资料优先，英文文本作为兼容场景评测。
- 首版为单企业、单机 Compose 部署；数据携带工作空间作用域，不等于支持多租户商业化运营。
- 同时满足项目现有的可部署、可演示、可测试和可解释交付目标；不将作品集展示结果等同于生产高可用能力。
- 企业规模、日活人数、使用频率、生产硬件、模型供应商、预算与正式上线日期待确认。

### 1.4 成功标准

以下五项为建议目标。安全门槛不得因样本小或性能不足而放宽；质量与体验阈值在阶段 0 建立基线后冻结。

| 编号 | 指标及建议目标 | 统计口径与验收方法 |
| --- | --- | --- |
| KPI-01 | 资料查找任务完成时间中位数较人工检索降低至少 30% | 至少 5 位试用者、每人 6 个任务；配对且交叉安排人工/平台任务，避免记忆偏差；计时至找到并核实正确证据，失败任务另报，不从报告隐去 |
| KPI-02 | 可回答问题合格率 ≥85% | 固定评测集中可回答子集；答案正确、关键点完整且无实质无依据结论才算通过；拒答也计失败 |
| KPI-03 | 引用支持率 ≥95%，应引用关键事实的覆盖率 ≥90% | 人工核对每条引用是否支持对应结论，并检查应有引用的事实；无引用不能通过减少分母获得高分 |
| KPI-04 | 未授权信息泄漏为 0，授权负向用例通过率 100% | 测试会话、文档、片段、引用、运行记录、统计、撤权、空知识库及提示注入；任何泄漏阻断发布 |
| KPI-05 | 核心业务端到端用例连续 10 次执行全部通过 | 干净测试数据完成登录→上传→就绪→问答→引用→刷新历史；真实 Agent 和依赖参与，保存版本、日志及测试证据 |

满意度、反馈率、活跃用户数作为观察项，不在没有试用规模的情况下设置虚构增长目标。性能目标及测量条件见 4.6。

## 2. User Experience & Functionality（用户体验与功能）

### 2.1 用户角色

| 用户画像 | 高频任务 | 主要痛点 | 成功体验 |
| --- | --- | --- | --- |
| 员工 Member | 查制度、理解产品、寻找操作说明 | 不清楚文档位置，无法确认答案依据 | 选中授权资料范围，一次提问后查看可验证引用 |
| 知识管理员 Admin | 维护资料、管理普通成员、排查入库失败 | 不知道资料是否可用、失败后怎么处理 | 明确看到文档状态、失败原因和受控恢复入口 |
| 工作空间负责人 Owner | 管理管理员、控制授权、查看使用效果 | 权限边界不清，无法判断平台是否有效 | 角色与授权可审计，统计不暴露员工私人问答 |
| 部署维护者 | 配置依赖、部署、备份与恢复 | 故障难关联，容器重启后结果不确定 | 健康状态可信，能用请求/任务标识定位问题 |

部署维护者是运维职责，不新增一个应用内超级用户角色。拥有机器权限不应被包装成日常查看员工正文的产品权限。

### 2.2 信息架构与页面

| 页面 | 主要信息与动作 | 可见范围 |
| --- | --- | --- |
| 登录 | 账号、密码、提交、登录失败提示 | 未登录用户 |
| 问答 | 本人会话、知识库选择、输入框、流式回答、引用、处理阶段、反馈 | 已登录且有授权知识库的成员 |
| 知识库列表 | 名称、说明、可用文档数、创建入口 | 用户授权范围；管理动作受角色限制 |
| 知识库详情 | 文档、格式、状态、上传时间、失败说明、切片查看、上传与删除 | 授权读取者；管理员执行管理动作 |
| 任务详情 | 当前状态、处理阶段、尝试次数、失败类型、恢复动作 | 有该知识库管理权的管理员 |
| 运行记录 | 状态、耗时、开始时间、关联标识 | 员工看本人；管理员看授权范围摘要 |
| 统计 | 调用量、成功率、延迟、入库状态与反馈分布 | Owner/Admin 的聚合权限 |
| 成员设置 | 成员、角色、启停状态、知识库授权 | Owner/Admin，具体动作见权限矩阵 |

默认登录后进入问答页。没有知识库权限时显示联系管理员的空状态；不自动勾选系统中所有知识库。首版不提供工作空间自由切换或公开注册。

### 2.3 权限矩阵

以下为基于架构角色定义的首版产品细化。知识库管理范围必须由后端显式授权；角色本身不是全局跨空间权限。

| 动作 | Owner | Admin | Member |
| --- | --- | --- | --- |
| 使用被授权知识库问答与查看片段 | 允许 | 允许 | 允许 |
| 读取本人会话与回答 | 允许 | 允许 | 允许 |
| 查看其他员工完整问答 | 默认禁止 | 默认禁止 | 禁止 |
| 创建/管理知识库、上传/删除文档 | 本空间管理范围 | 本空间管理范围 | 禁止 |
| 创建、禁用普通成员及调整其知识库授权 | 允许 | 允许 | 禁止 |
| 授予或撤销 Admin | 允许 | 禁止 | 禁止 |
| 查看聚合统计与管理审计 | 允许 | 按授权允许 | 禁止 |
| 重试失败入库任务 | 管理范围内允许 | 管理范围内允许 | 禁止 |
| 修改他人消息、绕过权限检索 | 禁止 | 禁止 | 禁止 |

首版不实现员工正文的额外授权机制；将来若确有需求，须单独设计权限、用途、审计与告知方式。Owner 转让、自助注销和工作空间销毁后置，禁止通过普通成员接口移除或降级最后一个 Owner。

### 2.4 核心用户流程

```text
管理员初始化成员与知识库授权
  → 上传资料 → 查看处理状态 → 文档 ready
  → 员工登录 → 选择授权知识库 → 输入问题
  → 检索与生成 → 流式答案 → done 后读取最终历史
  → 打开引用核对 → 提交有用/无用反馈

异常分支：
  上传不合规 → 拒绝并说明原因
  入库失败 → 分类显示 → 临时故障有限重试 / 永久失败修正文档
  结果未知 → 对账 → 确认成功或失败后恢复操作
  证据不足 → 明确说明资料不足，不编造企业事实
  SSE 无终态断开 → 显示已中断 → 查询运行状态及历史，不自动重提
  权限被撤销 → 拒绝后续读取并清理当前敏感视图
```

### 2.5 需求优先级和交付边界

- P0：业务 MVP 必须具备；缺失会破坏核心价值或安全边界。
- P1：首个完整交付版必须具备；可晚于 MVP，但不能省略后宣称完整交付。
- P2：后续候选，进入开发前另行确认需求和设计。

MVP 可以采用过渡入库流程，但须明确任务在进程重启时可能中断。V1.0 完整交付要求可靠入库、管理、统计、部署与故障验收全部完成。

### 2.6 用户故事与验收标准

#### FR-01 登录、刷新与退出 · P0

用户故事：作为企业员工，我希望使用被分配的账号登录并安全退出，以便只有本人能够访问我的问答。

- 正确账号密码登录后进入应用；错误账号或密码使用统一提示，不暴露账号是否存在。
- 无有效身份时业务接口拒绝访问；访问凭据过期可按契约刷新，刷新失败返回登录页。
- 退出后撤销刷新凭据、取消活动请求、清除敏感缓存；浏览器刷新不得重新看到上一用户正文。
- 禁用账号后新请求拒绝；已签发访问凭据不能绕过服务端成员有效性检查。
- 初始 Owner 通过有记录的部署初始化流程创建；不提供硬编码通用密码或隐藏入口。账号交付方式待确认。

#### FR-02 成员与知识库授权 · P0 权限基础 / P1 管理界面

用户故事：作为管理员，我希望分配成员可访问的知识库，以便员工只检索与职责相关的资料。

- 角色和动作符合 2.3；Admin 不得给自己或他人升级为 Owner/Admin。
- 每次资源操作校验成员有效性、工作空间归属及具体权限；请求中篡改 ID 不能越权。
- 提问提交时重新校验所选知识库；任一选择无权或失效则拒绝整次提交，不静默扩大/改变范围。
- 空知识库集合拒绝提问，不传成内部 `null` 或全库查询。
- 撤权后后续读取立即拒绝；已有流停止继续向客户端暴露新内容，前端清理相关视图。流中撤权的技术实现与延迟界限须在鉴权设计中明确并测试。
- 角色调整、禁用、授权变更记录操作者、目标、时间与结果；不要求删除历史审计。

#### FR-03 知识库创建与浏览 · P0

用户故事：作为知识管理员，我希望按资料主题建立知识库，以便组织文档并配置访问范围。

- 列表和详情仅返回当前作用域资源；显示名称、说明和可用文档数，不能把处理中数量标成可用数量。
- 创建包含名称和可选说明；空白名称拒绝，名称冲突返回明确冲突提示。
- 建议限制：名称 1～100 个字符、说明最多 1,000 个字符；实现前与 Agent 和数据库约束取交集并写入契约。
- 跨服务创建区分 pending、ready、failed；仅 ready 资源允许入库或问答。
- Agent 创建超时但结果未知时保留映射和关联标识，先对账，不提示已成功或自动重复创建。
- 首版不支持整库销毁、合并或批量迁移；修改已发布知识库信息的接口可在确有需求时补充，不假定原 Agent 已支持。

#### FR-04 文档上传与校验 · P0

用户故事：作为管理员，我希望上传企业文档并获得明确结果，以便资料能够参与问答。

- 首版支持单文件 txt、md、pdf、docx；单文件上限 20 MiB，最终采用 Go、代理与 Agent 支持上限的较小值。
- 校验实际内容、扩展名、请求大小和权限；拒绝空文件、伪装格式、危险路径及不支持类型。
- 文档进入持久化受控目录后才确认已接收；使用随机存储名，原文件名仅为展示元数据。
- “上传完成”仅指接收成功；页面持续展示处理状态，不能直接标为可检索。
- 扫描图片型 PDF、无可提取正文或解析失败的文档给出明确原因；不宣称支持 OCR。复杂表格与版式可能丢失语义，评测与界面帮助中说明限制。
- 同名文件不自动覆盖旧文档；以不同平台文档 ID 区分，显示上传时间。相同提交的重试与用户主动再次上传必须区分。
- 请求超时不能自动重新上传；查询已受理记录或进入结果核对流程。

#### FR-05 文档状态与可靠任务 · P0 状态 / P1 可靠恢复

用户故事：作为管理员，我希望知道文档在哪个阶段失败并安全恢复，以便资料处理不会无声丢失或重复。

- 展示排队、处理、成功、失败和结果核对状态；只有解析、切块、嵌入与索引完成且可查询才标为可用。
- 支持阶段说明，不以虚构百分比表示进度；没有精确进度时使用不定进度。
- 临时故障有限重试，永久格式错误直接失败；重试次数、下一次计划与脱敏原因可查。
- V1.0 必须验证 Worker 崩溃、消息重投和 Agent 成功响应丢失；同一 job_id 不能产生重复文档副作用。
- 人工重试需管理权限；结果未知时先对账，不允许绕过核对重复执行。
- 建议自动重试上限为 3 次，采用退避；最终次数、等待时间、租约和对账周期由可靠任务 ADR 冻结。
- 过渡版明确标注 BackgroundTasks 的恢复限制，不提供无法兑现的“自动恢复”承诺。

#### FR-06 文档与片段查看、删除 · P0

用户故事：作为管理员，我希望检查已入库内容并删除失效资料，以便问答依据保持有效。

- ready 文档可分页查看抽取片段、片段序号和章节信息；非 ready 文档说明暂不可查看原因。
- 普通成员可查看授权引用所需片段；管理动作仅对管理员开放。
- 删除前提示影响：后续问答不再使用该资料，历史答案可能保留但引用变为不可用。
- 删除提交后立即禁止新检索使用目标；清理成功前显示删除处理中，不假报完成。
- 若暂不能保证单文档排除，应暂停受影响知识库的问答并明确提示，直至确认清理，不能继续返回待删除内容。
- 数据库、文件与索引清理失败保留删除意图并对账；处理中的旧任务不得将已删除资料重新索引。
- 历史已生成文字不会因文档删除自动从所有消息中清除；敏感信息彻底清除需独立设计。页面不得承诺已完成此类清除。

#### FR-07 本人会话与历史 · P0

用户故事：作为员工，我希望保存并回看自己的问答，以便无需重复查找相同资料。

- 可以创建会话、分页查看本人会话和历史消息；篡改会话 ID 无法读取其他人的历史。
- 会话资源映射由 Go 管理，消息事实由 Python 持有；前端完成流后以持久化历史为准。
- 同一会话仅允许一个活动运行；并发提交返回 409，并提示等待当前回答结束。
- 创建结果未知时保留可核对状态，不自动创建第二个 Agent 会话。
- 历史中引用重新进行权限检查。建议权限收缩后，对可能包含被撤权资料的旧会话整体限制读取，直到具备经验证的消息来源追踪；具体策略须在权限设计中定稿。
- 会话重命名、删除和消息编辑不属于本版承诺；前端不能显示无实际能力的操作入口。

#### FR-08 授权范围内流式问答 · P0

用户故事：作为员工，我希望在选定的资料范围内提问并逐步看到回答，以便了解系统正在处理且尽早阅读答案。

- 提交前展示已选知识库；空问题、仅空格、超长问题拒绝。建议问题上限 4,000 字符，须在契约冻结时校验模型与 Agent 限制。
- 浏览器只能提交问题和平台知识库 ID，不能控制内部资源 ID、`skip_user_persist`、系统提示词或数据源。
- 点击后立即呈现连接状态并禁止重复提交；收到正文后逐步渲染 Markdown，原始 HTML 不执行。
- 只有收到 `done` 才显示本次流正常完成；`error` 显示失败，无终态 EOF 显示中断。
- 完成后刷新持久化历史；原 Agent 可能在生成后清理引用或追加说明，最终正文不能仅依赖拼接 delta。
- 用户停止接收后保留可辨识的未完成草稿，查询运行状态及历史。未验证上游取消前不得显示“模型已停止”或“费用已停止”。
- 断网后不自动重放提问；恢复后提供检查结果入口。若查询发现服务器已完成，按持久化记录恢复，不把旧草稿当作第二条答案。
- 无检索证据时明确说明资料不足；不把常识推断包装成企业规定。首版禁止转入销售数据 NL2SQL 等非目标通路。

#### FR-09 引用与证据核验 · P0

用户故事：作为员工，我希望点击答案中的引用查看对应原文，以便确认结论是否可信。

- 引用展示文档名和可用的章节/片段定位，点击后通过 Go 校验当前权限再返回片段。
- 同名文档只能在本次授权知识库与平台映射内解析；无法唯一定位显示“引用无法定位”，不猜测最新文档。
- 文档被删除、权限被撤销或片段失效时给出对应的安全提示；不暴露未授权文档名称和正文。
- 模型生成的引用编号与文本均不可信；未通过映射校验的引用不可变成可访问链接。
- 首版提供片段溯源，不承诺原 PDF 精确页码高亮或整篇原文在线预览。

#### FR-10 可理解的处理过程 · P0

用户故事：作为员工，我希望看到检索、生成等处理阶段，以便知道等待发生在哪里。

- 展示检索中、证据检查、生成中、自检中等受控摘要，可折叠查看；不是每次问答都必须经过所有阶段。
- 保留协议事件兼容性，但不直出内部提示词、推理正文、SQL、供应商错误或未授权片段。
- 多轮检索与反思准确体现轮次；达到上限后给出限制说明，不无限循环。
- 首个阶段事件到达不能作为首个答案 token 到达计入性能统计。

#### FR-11 运行记录 · P1

用户故事：作为员工或管理员，我希望根据运行状态和关联标识定位失败，以便判断是否需要重试或联系维护者。

- 每次已受理问答有平台 run_id，记录开始/结束时间、终态、耗时、脱敏错误分类及 request_id。
- 员工只能查看本人记录；管理员可看管理范围摘要，摘要不包含完整问题或答案。
- 运行状态以持久化记录为准；进程异常退出后的 running 记录通过恢复机制收敛，不能永久假运行。
- 对结果未知的操作显示核对提示，恢复策略不通过重复发送问题实现。

#### FR-12 回答反馈 · P1

用户故事：作为员工，我希望标记答案是否有用并描述问题，以便管理员识别知识缺口。

- 已持久化答案可提交有用/无用及可选原因；建议原因包括资料不足、答案错误、引用不匹配、表达不清。
- 同一用户对同一答案只保留一条当前反馈，允许更新；后端校验答案属于该用户可访问会话。
- 建议补充文字上限 500 字符；不自动复制整段问答到反馈记录或日志。
- 管理员默认仅见聚合反馈，不通过反馈接口获得员工正文。反馈失败可重试且不制造重复记录。

#### FR-13 聚合统计 · P1

用户故事：作为管理员，我希望查看调用与入库情况，以便判断平台是否稳定及资料是否得到使用。

- 提供按日期筛选的运行数、完成/失败/中断数、成功率、答案首 token 与总耗时分位数、任务状态数量、反馈分布。
- 成功率为 completed / 已进入终态运行数；活动运行单列，前置拒绝请求另计，不混入运行分母。
- 延迟统计注明样本数与口径；未收到正文的运行不伪造首 token 值，独立报告占比。
- 数据由 Go 聚合接口返回；无数据展示空状态，不能用随机曲线填充。
- token 用量无法获得时标为未知；未配置供应商价格与币种不显示推算费用。
- 图表提供文字或表格替代，筛选和分页可通过 URL 恢复。

#### FR-14 部署与运维交付 · P1

用户故事：作为维护者，我希望按文档部署和恢复系统，以便演示或试点不依赖开发者机器的隐含配置。

- 提供固定镜像版本、配置样例、初始化与迁移步骤、启动/停止及排障说明。
- 仅 Nginx 对外提供服务；Go、Agent 与数据组件按部署基线置于内部网络。
- 存活检查与业务就绪检查分离，关键依赖不可用时不报告整体就绪。
- 数据与上传文件使用持久卷；容器重启后资料、会话与任务记录保留。
- 在测试环境完成备份恢复和兼容版本回退演练；记录恢复范围与缺失窗口，不用删除持久卷作为恢复手段。
- 提供真实的已知限制、评测和压测报告；Compose 单机部署不宣称高可用。

### 2.7 通用交互要求

- 每个页面具备加载、空、错误、成功、无权限与禁用状态；错误附可复制的请求标识，不暴露堆栈。
- 只读请求可有限重试；涉及创建、上传、提问等副作用的错误提示区分“未受理”和“结果待确认”。
- 删除等有影响的操作展示资源名称与后果；按钮忙碌时防止双击提交，后端仍负责并发与幂等。
- 320px 宽度与 200% 文本放大下核心流程可用；支持键盘、可见焦点、表单标签与错误关联。
- 流式生成不持续抢焦点；用户上滚查阅时不强制滚回底部，提供回到底部入口；状态朗读不逐 token 打断。
- 颜色不作为唯一状态标识；图表、弹窗和抽屉提供相应的文本、焦点与键盘支持。
- 时间按用户界面时区展示并标明口径，接口统一 UTC；列表采用稳定排序和分页。

### 2.8 非目标

本版不包含：商业化多租户 SaaS、支付计费、公开自助注册、SSO、外部知识源自动同步、团队任务协作、可视化工作流编辑器、自研模型训练、Kubernetes、服务网格、OCR、多模态问答、NL2SQL、任意联网搜索、高级检索实验台、自动重生成、断线续传、文档版本合并和知识库销毁。

不承诺模型回答绝对正确、撤回用户已经看到的内容、停止浏览器接收即停止计费、任何历史资料均可完美解析或至少一次投递等同恰好一次执行。

## 3. AI System Requirements（AI 系统要求）

### 3.1 AI 能力边界

首版复用现有 Python Agent 的解析、切块、嵌入、向量/关键词检索、融合、生成与反思能力。Go 负责可信的授权范围、运行管理和输出边界。模型不能决定用户权限，也不能从文档中的指令获得额外工具权限。

现有算法与提示词优先保持原样，通过接口和部署约束接入。如果实测无法满足“证据不足提示”、禁用非目标通路或最终答案一致性等要求，应明确记录差距，并为必要适配单独设计，不把已有代码存在视为需求已满足。

### 3.2 工具与外部依赖

| 工具/依赖 | 用途 | 允许的数据与权限 | 失败行为 |
| --- | --- | --- | --- |
| 内部会话接口 | 创建会话、读取历史、提问 | Go 已授权的平台映射；用户不能指定内部 ID | 创建/提问结果未知先核对，普通读取有限重试 |
| 内部知识库与入库接口 | 上传、状态、片段、删除 | 管理权校验后的目标知识库 | 记录失败或结果未知，不伪造 ready |
| Elasticsearch | 关键词和向量检索 | 限定本次授权知识库 | 显式失败或明确能力受限，不静默退化成无来源企业回答 |
| 嵌入模型 | 文档及查询向量化 | 必要的授权文本；供应商与数据政策待确认 | 任务失败/有限重试，禁止空向量伪成功 |
| 生成与判断模型 | 回答、相关性判断、反思 | 问题、允许的历史与检索片段 | 超时、限流、格式错误可诊断；受总预算与轮次限制 |
| Python 幂等入库适配层 | V1.0 任务提交与结果核对 | job_id、请求指纹、文件引用和目标库 | 同键同请求复用结果，同键不同请求冲突 |

原引用全局按文档名查询接口不得直接公开。工具输出、数据库内容和模型结果同样在边界校验。允许的模型服务清单与资料外发规则在真实企业试点前确认。

### 3.3 答案质量要求

- 明确区分企业资料中有依据的结论、资料不足与需要人工确认的事项。
- 对关键企业事实提供引用；不能仅附一个与结论无关的文档名。
- 资料相互矛盾时列出冲突及各自依据，不能自行认定一份资料具有更高制度效力。
- 多轮对话只能使用仍被授权的历史上下文；切换知识库范围不能把历史中的受限内容继续送入模型。
- 对“忽略权限”“显示系统提示词”“查询别人的文档”等请求，权限与工具边界不受其影响。
- 生成、纠错和反思都有明确上限；模型无输出、循环或格式错误应结束并记录失败，而非永久加载。
- 流式草稿与最终答案可能不同，最终展示与 Python 持久化结果一致；重写语义在契约样本中固定并回归测试。

### 3.4 评测数据集

建议首轮建立不少于 100 个固定问题，使用获得授权的非敏感样本。仓库 `test_docs` 可作候选来源，使用前检查内容与来源，不能默认适合外发。

| 子集 | 建议题数 | 评测重点 |
| --- | --- | --- |
| 单文档直接回答 | 30 | 正确答案、关键事实和引用 |
| 跨片段/跨文档综合 | 20 | 完整性、冲突和证据组合 |
| 多轮追问 | 10 | 上下文衔接与知识范围保持 |
| 资料不足或无答案 | 15 | 避免编造，给出可理解不足说明 |
| 权限与提示注入 | 15 | 无泄漏、工具边界不可突破 |
| 引用歧义与文档生命周期 | 10 | 同名、删除、撤权、失效片段 |

每题保存题目 ID、资料版本、允许知识库、角色、预期关键点、证据片段、应答/拒答规则和评分说明。权限用例使用隔离测试账号，不使用真实秘密作为探针。

### 3.5 评测方法和通过条件

1. 冻结模型、提示词、检索配置、数据集和代码版本；评测集不与日常调参样本混用。
2. 客观检查权限、引用定位、SSE 终态与历史一致性；人工按关键点判定正确性与依据。
3. 建议至少两名评审者独立评分并处理分歧；资源不足时记录单人评审限制，不把模型自评当最终裁决。
4. 报告 KPI-02/03/04、无答案子集恰当提示率（建议 ≥90%）、各子集表现、样本数及失败样例。
5. 对关键安全场景重复运行并增加接口级确定性测试；一次未泄漏不构成生产隔离证明。
6. 模型、检索配置、权限映射、解析器或提示词变更后执行相应回归；安全回归失败立即阻断发布。

用户点赞仅作为体验信号，不替代事实正确性评测。所有“达到指标”的说明必须附实际评测报告。

### 3.6 时延与成本控制

记录各阶段耗时、模型调用次数、可获得的 token 用量和失败分类；统计默认不保存完整提示词或文档正文。配置总调用时限、反思轮次、检索条数、并发与输出上限，且不能由普通用户任意增大。

模型价格、日预算和单次调用预算待确认。无法得到准确用量时显示未知；不能将停止 UI 接收视为停止上游资源消耗的依据。

## 4. Technical Specifications（技术规格）

### 4.1 架构与依赖方向

```text
浏览器 React 19 / TypeScript
              │ 同源 HTTPS，HTTP + POST SSE
            Nginx
              │
           Go / Gin ── 内部鉴权 HTTP/SSE ── Python Agent
              │                               │
      platform MySQL / Redis          agent MySQL / Elasticsearch
              │
         事务 Outbox → RabbitMQ → Go Worker → Python 入库适配层
              │
         持久化上传文件（受控 volume）
```

Go 是唯一公开业务入口，采用模块化单体，API 与 Worker 是两个进程入口。模块内依赖为 transport → application → domain，基础设施实现内层端口。前端依赖 app → feature 公开接口 → shared。领域规则不得依赖框架或供应商 SDK。

前端沿用 React Router、Tailwind、TanStack Query、Zustand、ECharts；后端沿用 GORM/MySQL、Redis、RabbitMQ、Zap；Agent 保留现有技术。本文不新增框架或基础设施。

### 4.2 数据所有权与主要实体

| 实体/事实 | 唯一写入方 | 最小业务信息及约束 |
| --- | --- | --- |
| 用户、登录会话 | Go | 用户状态、密码哈希、刷新凭据哈希、轮换/撤销信息 |
| 工作空间与成员 | Go | workspace_id、user_id、角色、状态；保护最后一个 Owner |
| 平台知识库与授权 | Go | 平台 ID、工作空间、名称、访问授权、创建状态 |
| 资源映射 | Go | 平台 ID、Agent 实例和资源 ID、归属、状态；映射唯一 |
| 会话归属、问答运行 | Go | owner、作用域、run 状态、时间、错误摘要；同会话一个活动运行 |
| Agent 会话、消息、决策日志 | Python | 历史与最终回答的事实源；Go 经内部 API 读取 |
| RAG 文档、切片、向量、索引 | Python | 内容与检索事实；Go 不直接操作其表 |
| 上传、入库任务、Outbox、消费记录 | Go | 文件引用、job_id、请求指纹、状态、重试、租约、删除意图 |
| 审计、反馈、统计摘要 | Go | 作用域、操作者、关联 ID、最小必要字段；不复制完整消息历史 |

可使用同一 MySQL 实例中的独立 platform/agent 数据库和独立账号。Redis 不是业务事实的唯一存储。物理表结构、索引和数据保留策略在相应设计与 migration 中明确。

### 4.3 状态与一致性

| 对象 | 状态模型 | 核心规则 |
| --- | --- | --- |
| 跨服务创建映射 | pending → ready / failed | 结果未知保持可核对状态；不能盲重试或宣称跨服务事务 |
| 问答运行 | running → completed / failed / interrupted | done 是正常流完成信号；恢复查询只能基于可信的持久化事实修正状态 |
| 客户端流 | idle → connecting → streaming → completed / failed / interrupted / cancelled | cancelled 仅代表客户端接收停止，不自动代表 Agent 取消 |
| 可靠入库任务 | queued → processing → succeeded / failed；processing ↔ reconciling | 对账确认后进入确定终态；重试和租约规则必须持久化 |
| 处理阶段 | parsing → chunking → embedding → indexing | 阶段不是精确百分比；阶段失败须关联 job_id |
| 文档删除 | 建议 active → deleting → deleted，失败保持待恢复删除意图 | 先停止新使用再清理，禁止旧任务复活内容；具体字段由 ADR 定义 |

跨服务失败路径：Go 记录已受理操作与映射 → 调用 Agent → 确认结果并更新状态；超时不能判断未执行，必须进入核对。问答没有可证明的内部幂等与取消保证时，不自动重发。

可靠入库路径：文件持久化 → 同事务写任务与 Outbox → 发布确认 → Worker 提交幂等入库 → 核对并保存终态 → ACK。Agent 成功后 Worker 崩溃的重投必须复用原结果。至少一次投递不等于端到端恰好一次。

| `/knowledge-bases/{id}/documents/{document_id}` | DELETE，受控删除 | FR-06 |
| `/knowledge-bases/{id}/documents/{document_id}/chunks` | 建议 GET，授权片段读取 | FR-06/09 |
| `/ingestion-jobs/{id}` | GET，任务状态 | FR-05 |
| `/ingestion-jobs/{id}/retry` | 建议 POST，受控人工重试 | FR-05 |
| `/chat/sessions` | GET/POST，本人会话列表与创建 | FR-07 |
| `/chat/sessions/{id}/messages` | GET，本人历史 | FR-07 |
| `/chat/sessions/{id}/runs` | POST，流式问答 | FR-08/10 |
| `/chat/runs/{id}` | GET，运行状态与摘要 | FR-11 |
| `/chat/runs` | 建议 GET，作用域化分页运行记录 | FR-11 |
| `/chat/runs/{id}/citations/{citation_id}` | 建议 GET，绑定运行上下文的安全引用解析 | FR-09 |

| `/analytics/overview` | GET，聚合统计 | FR-13 |

一般响应使用 `data/request_id`；失败使用 `error.code/error.message/request_id`。采用真实 HTTP 状态码：400 校验、401 未认证、403 禁止、404 不存在或隐藏资源、409 冲突、413 过大、415 不支持格式、429 限流、503 依赖不可用；超时按契约区分。SSE 开始后只能通过事件报告错误。

JSON 字段为 snake_case，平台 ID 为字符串，时间为 UTC RFC3339。普通分页默认 20、上限 100；内部 Agent 片段分页存在不同上限，适配层不得假定完全相同。文件和 SSE 不采用普通 JSON 包装。

内部 Agent 接口由 AgentClient 统一封装，包括创建会话、历史、ask、知识库与文档状态、上传和片段。不得把 Python 路由直接透传为公开接口。

SSE 必须满足：

- 使用 fetch + ReadableStream 处理 POST SSE；不使用只支持 GET 的原生 EventSource 发问题。
- 保留 router、rewrite、retrieve、grade、correct、generate、reflect、citation、done、error 事件；附 run_id、request_id 和递增 seq。
- 处理 UTF-8 跨块、CRLF、多行 data、多个事件、半包；未知扩展事件可记录并忽略，畸形协议结束运行。
- 代理关闭缓冲并及时 Flush；重复/倒退序号按冻结契约处理，不重复渲染。
- 单独记录生成后正文修正和最终持久化样本，覆盖前端草稿与历史的一致性。

### 4.5 安全、隐私与保留策略

- 所有外部输入在边界验证；权限在应用层与带作用域的数据查询中强制，不能只隐藏按钮。
- Access JWT 仅在前端内存；刷新凭据 HttpOnly，生产 Secure，服务端仅存哈希并支持轮换撤销；Cookie 操作校验 Origin/CSRF。
- 内部 Agent 地址来自受控配置，客户端不能指定 URL；内部请求有服务鉴权、连接超时和总时限。
- 文件隔离存储，受限解析资源，不执行宏或外部内容；Markdown 原始 HTML 不执行，链接协议受限。
- 日志默认不记录密码、Cookie、令牌、模型密钥、完整问题、回答和文档。审计只记录必要操作元数据。
- 首版只开放单企业；Agent 全链路隔离没有证据前不得对外宣称多租户安全。
- 文档权限撤销还影响历史正文及模型上下文，不能只关闭引用按钮。历史隔离策略为上线前必须完成的设计项。
- 资料可能发送给配置的模型供应商；供应商、保存/训练政策、地域和企业许可待确认。未确认前只用非敏感演示资料联调。
- 消息、原文件、索引、任务、审计、反馈和备份的保留时长待确认；不默认自动清理。上线前明确删除范围、恢复窗口、备份过期及责任人。

### 4.6 非功能目标与容量假设

下列数值是初始建议，不是实测容量或 SLA。压测前记录 CPU、内存、存储、网络、模型、文件大小分布、数据条数及配置；硬件未确定时不得声称达标。

| 维度 | 建议验收目标 | 方法与限制 |
| --- | --- | --- |
| 普通 API | P95 ≤500ms | 在约 10,000 条平台记录、20 个并发客户端下测不含模型/上传的接口；同时报告错误率与数据库条件 |
| 真实问答首正文 | P95 ≤10s | 5 个并发问答、固定 50 个问题、模型与检索集固定；从提交到首个答案 token，不把阶段事件算正文 |
| 问答总耗时 | P95 ≤60s | 与首正文相同条件；另报失败、无答案、超时比例，不能只报告成功样本 |
| 可用性 | 非注入故障压测中服务错误率 <1% | 报告测量时长与样本数；不据此推导月度 SLA |
| 流式转发 | 模拟 Agent 下 20 条并发流无串流、丢终态或持续资源泄漏 | 与真实 Agent 测试分开报告，不能等同模型吞吐能力 |
| 入库 | 建议 1 MiB 以内纯文本文件 P95 ≤120s | 排队与处理耗时分开，10 份代表性资料起测；其他格式单独测量，不承诺同一阈值 |
| UI 可访问性 | 核心流程键盘可达，320px/200% 放大可用 | 自动检查加人工验证；不凭使用组件库宣称全站合规 |
| 恢复 | 重启后数据保留，未完成任务可恢复或进入明确可诊断状态 | 注入 API/Worker/Agent 重启并核对数据与副作用；RPO/RTO 待部署要求确认 |

问答、上传、列表、文件解析和 Worker 均有明确资源上限。若基线测量不满足建议目标，先定位依赖与瓶颈，再决定优化或调整产品预算，不能放宽安全检查换性能。

### 4.7 观测与事件口径

业务事件建议包括 login_result、document_accepted、ingestion_terminal、run_started、run_terminal、citation_opened、feedback_updated。只保存作用域 ID、结果、时间、耗时及关联 ID 等必要信息，不附正文。

运行和任务各以 run_id/job_id 去重统计；重试次数单列，不把一次用户操作的重投计作新增成功业务。聚合统计明确时间范围、时区、样本量与缺失值。维护者可通过关联标识追踪 HTTP→任务→Agent，避免把高基数 ID 作为指标标签。

### 5.3 必要设计决策与回退

设计至少说明背景、决定、备选方案、依赖方向、数据所有者、安全影响、失败路径、迁移/回退和验证证据。本文提出产品目标，不代替这些实现决策。
