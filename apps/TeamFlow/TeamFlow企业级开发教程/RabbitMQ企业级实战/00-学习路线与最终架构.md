# TeamFlow RabbitMQ 企业级实战：学习路线与最终架构

> 本专题不是“会发一条消息”就结束，而是用 TeamFlow 的任务通知链路，循序完成从 RabbitMQ 零基础到可解释、可验证、可运维的企业级实现。

## 本节目标

- 明确本专题的最终业务目标、学习顺序和每阶段验收标准。
- 理解 RabbitMQ 在 TeamFlow 中解决的问题，以及它不能解决的问题。
- 知道每一阶段应新增哪些代码，何时才应引入 Confirm、死信、Outbox 和集群。
- 建立正确的可靠性模型：至少一次投递加业务幂等，而非承诺 Exactly Once。

## 前置条件

- 已能运行当前 TeamFlow 的 Go、MySQL、Redis 和 WebSocket 基础链路。
- 了解 Go 的 package、interface、`context.Context`、goroutine 与基本单元测试。
- 已完成教程中的任务系统和 WebSocket 章节更佳，但不要求有 RabbitMQ 经验。

## 为什么 TeamFlow 要接入 RabbitMQ

当前任务分配与状态变更会在 HTTP 请求内直接调用通知服务。这样实现简单，却有三个边界：

1. 任务写库成功后，WebSocket 推送失败时，任务已成功而通知可能丢失。
2. 通知、邮件、审计等下游能力会让请求链路越来越长，也越来越难扩展。
3. HTTP 服务重启、下游抖动、突发流量时，缺少可观测的缓冲与恢复机制。

RabbitMQ 用来将“发生了什么”与“谁要处理它”解耦。任务服务只发布领域事件；通知 Worker 独立消费并处理。它不是数据库，不保存业务真相，也不能单独消除 MySQL 写入和消息发布之间的双写窗口。

## 最终业务闭环

```text
用户请求：分配任务 / 改变任务状态
    │
    ▼
Task Service
    │ 同一 MySQL 事务
    ├── 写 tasks
    └── 写 outbox_events
    │
    ▼
Outbox Relay ── Publisher Confirm + mandatory Return ──► RabbitMQ
                                                       │
                                                       ▼
                                      teamflow.events.v1 (topic exchange)
                                                       │
                                                       ▼
                                teamflow.notification.websocket.q (quorum)
                                                       │
                                                       ▼
Notification Worker
    │ 同一 MySQL 事务
    ├── 写 processed_messages（幂等）
    └── 写 notifications（用户可查询的真相）
    │
    ├── 成功：manual ACK
    └── 失败：有限重试 → DLX → 停车场
    │
    ▼
WebSocket 尽力实时推送；离线或推送失败时，客户端查询 notifications
```

## 不变量：每一阶段都不能破坏的规则

- 任务表与通知表的业务真相只在 MySQL；RabbitMQ 只传递事件。
- HTTP Controller、Gin Handler 和业务 Service 不直接依赖 `amqp091-go` 类型。
- 一个 AMQP Channel 只能被一个 goroutine 使用；不在每个 HTTP 请求中 Dial RabbitMQ。
- 不在业务成功前 ACK；消费者可重复收到消息，处理必须按 `event_id` 幂等。
- 不无限 `NACK requeue`；临时错误有限重试，永久错误进入停车场。
- WebSocket 推送不参与消息 ACK 的成功条件；通知先落库，推送后置。
- 不删除现有 Redis Stream 教程和代码。二者用于比较，迁移必须渐进且可回退。

## 推荐目录边界

本专题统一使用 `internal/messaging/rabbitmq`，避免和现有 `internal/mq/stream.go` 混淆。后续章节与代码都遵守这个边界。

```text
config/
  config.go                    # RabbitMQConfig、环境变量与校验
  config.yaml

internal/event/
  event.go                     # 与 AMQP 无关的事件信封
  task_event.go                # task.assigned.v1 等业务载荷

internal/messaging/rabbitmq/
  connection.go                # 长连接、Channel owner、关闭观测
  topology.go                  # exchange / queue / binding 的唯一常量来源
  publisher.go                 # Confirm、Return、发布结果
  consumer.go                  # QoS、manual ACK、投递分派
  retry.go                     # 错误分类、重试与死信策略
  health.go                    # 就绪状态与连接状态

internal/worker/
  notification_worker.go       # 通知事件处理、落库和 WebSocket 推送
  outbox_relay.go              # 领取、发布、确认和恢复 Outbox 事件

internal/model/
  outbox_event.go
  processed_message.go

internal/repository/
  outbox_repository.go
  processed_message_repository.go

cmd/
  main.go                      # HTTP API
  worker/main.go               # 独立 notification/outbox worker

deploy/rabbitmq/
  definitions.json             # 可选的受控拓扑定义
  rabbitmq.conf
  enabled_plugins

docker-compose.rabbitmq.yml
```

`internal/event` 定义业务语言，不能 import RabbitMQ。`internal/messaging/rabbitmq` 只负责 AMQP 技术细节，不知道 Task、Notification 的字段。Worker 负责两者之间的转换与业务处理。这样的分层能让单元测试用假的 `EventPublisher` 替代 RabbitMQ。

## 学习与实现路线

Level 2 的可跟做章节见：[10-Level2-任务分配事件与通知消费者.md](10-Level2-任务分配事件与通知消费者.md)。

Level 3 的可靠性实践见：[11-Level3-Confirm-ACK-重试与死信.md](11-Level3-Confirm-ACK-重试与死信.md)。

### Level 0：环境与消息模型（零基础）

**学习内容**：Broker、Connection、Channel、Exchange、Queue、Binding、Routing Key、Consumer、ACK；direct/topic/fanout/headers 四种 Exchange 的适用边界。

**动手结果**：用 Docker Compose 启动单节点 RabbitMQ，能进入管理台，能用临时队列完成四类路由实验。

**必须回答**：一条 `task.assigned.v1` 消息经过 topic exchange 后为什么进入某个队列；没有 binding 时为什么不会自动被消费。

**完成标志**：能从管理台区分 Ready、Unacked、Consumers，并能定位消息路由到哪里。

### Level 1：项目最小接入（会连接，不谈可靠消息）

**学习内容**：官方 Go 客户端 `github.com/rabbitmq/amqp091-go`、AMQP URI、vhost、配置校验、连接与 Channel 生命周期。

**代码结果**：

- `config.Config` 新增 `RabbitMQConfig`；URI、heartbeat、timeout、prefetch 和并发度可由环境变量覆盖。
- API 进程持有长期 publisher connection；Worker 持有独立 consumer connection。
- 拓扑使用固定名称：`teamflow.events.v1`、`teamflow.dlx.v1`、`teamflow.notification.websocket.q`。
- Channel 有唯一 owner；发生协议错误后废弃旧 Channel 而非继续复用。

**完成标志**：启动时可声明同一套 durable 拓扑两次而不冲突；并发 HTTP 请求不会共享同一个 Channel。

**后续衔接章节**：第 07 节 TeamFlow 消息拓扑设计、第 08 节引入官方 Go 客户端、第 09 节连接与 Channel 生命周期。完成第 01–06 节基础实验后，再按此顺序编写并实践。

### Level 2：第一条真实业务事件（会发布和消费）

只选择一个切片：`AssignTask` 成功后产生 `task.assigned.v1`。不要同时改任务状态、评论、邮件和审计。

**事件信封最小字段**：

```text
event_id          全局唯一 ID，用于幂等
event_type        task.assigned.v1
schema_version    1
occurred_at       事件发生时间
correlation_id    请求链路关联 ID
causation_id      触发该事件的上游事件 ID（首事件可为空）
trace_id          可观测性关联字段
payload           task_id、project_id、assignee_id、operator_id
```

**代码结果**：Task Service 只调用 `EventPublisher` 接口；通知 Worker 订阅任务事件、创建通知记录、再尝试 WebSocket 推送。

**完成标志**：关闭 HTTP API 后单独启动 Worker，仍能消费已有消息；用户离线时通知仍在 MySQL 中可查询。

### Level 3：发布与消费可靠性（理解消息可能失败）

按下面顺序逐项增加，不要一次性封装成“万能 MQ 客户端”。

1. **持久化**：durable exchange/queue 加 persistent message，保证 Broker 正常持久化语义。
2. **Publisher Confirm**：Broker 接管消息后才确认发布结果；超时、连接中断都属于 unknown outcome。
3. **mandatory + Return**：无 binding 的不可路由消息必须进入错误处理和告警，不能静默丢弃。
4. **manual ACK + QoS**：Handler 的数据库事务提交后才 ACK；用 prefetch 控制未确认消息数量。
5. **有限重试**：按临时错误、永久错误、未知错误分类；退避、最大次数、停止条件都必须明确。
6. **死信停车场**：超出重试次数或永久失败进入 dead queue；人工诊断、修复和受控重放，而非直接 purge。

**完成标志**：主动制造无 binding、数据库短暂失败、Worker 在 ACK 前退出等故障，能从日志和管理台解释最终消息状态。

### Level 4：一致性与幂等（企业级分水岭）

Confirm 只说明 RabbitMQ 是否接管消息，不能解决“任务事务已提交、进程却在 publish 前崩溃”。所以本阶段引入 Transactional Outbox。

**生产者侧**：`TaskService.AssignTask` 的同一个 MySQL 事务中同时写任务变更和 `outbox_events`。Relay 用短事务领取待处理记录，发布并等待 Confirm；确认后标记已发布。若 Relay 在 Confirm 后、标记前崩溃，事件会再次投递。

**消费者侧**：Notification Worker 在同一个 MySQL 事务内写 `processed_messages(event_id UNIQUE)` 与 `notifications`。如果业务已提交但 ACK 未到达 Broker，重复消息到来时唯一约束让它成为安全的空操作。

**完成标志**：验证两种重复窗口：Relay Confirm 后崩溃、Worker 业务提交后 ACK 前崩溃；最终只有一条用户通知，且事件不会无声消失。

### Level 5：生产工程（让系统可运行、可恢复、可审计）

**连接与停机**：连接关闭后退避重连，重新声明拓扑和 Consumer；停机时先停止领取 Outbox/新投递，再等待有界时间完成在途事务，超时后由 Broker 重投未 ACK 消息。

**可观测性**：日志至少带 `event_id`、event type、routing key、queue、attempt、trace ID、耗时和结果。指标至少覆盖发布成功/失败/Return、Confirm 延迟、消费成功/失败/死信、Ready、Unacked、重连次数与 Handler 时延。

**安全**：开发、测试、生产分 vhost；publisher、worker、topology、ops 分别使用最小权限账户；生产仅使用 Secret 注入凭据和 TLS，不提交真实 URI。

**容量与高可用**：单机用于开发和 CI；关键持久队列在生产评估 Quorum Queue 和三节点多数派。容量结论必须基于消息大小、Confirm window、consumer 数、Handler 耗时、磁盘与故障恢复压测，而不是写固定 QPS。

**完成标志**：可以演练 Broker 重启、网络抖动、MySQL 不可用、毒消息、积压恢复和单节点故障，并用告警与数据不变量说明恢复结果。

## 常见误区

| 误区 | 正确做法 |
| --- | --- |
| RabbitMQ 持久化后就绝不丢消息 | 持久化只是一个环节；还需要 Confirm、Return、Outbox、幂等和故障验证。 |
| 收到消息立刻 ACK | 先完成可回滚的业务事务，再 ACK。 |
| 失败就无限 requeue | 使用有限次数和退避；毒消息送停车场。 |
| WebSocket 推送成功才算通知成功 | 通知落库才算成功，WebSocket 只是实时体验层。 |
| 一个连接和 Channel 足够所有 goroutine 使用 | Connection 可以长期复用；每个 Channel 必须有唯一 owner。 |
| 搭好三节点就天然高可用 | Quorum 需要多数派、正确磁盘与网络设计、压测和故障演练。 |
